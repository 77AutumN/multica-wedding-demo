# 婚宴 Demo 0.1.0

## 调用

在原生当前 Run 目录写 UTF-8 无 BOM JSON，然后执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\Multica-CRM-Trial\ops\Invoke-WeddingDemo.ps1 -RequestFile ./wedding-request.json
```

先阅读 [固定请求格式](references/requests.md)。不使用绝对请求路径，不在工作目录外创建请求。不要直接执行 CLI、修改工具、连接配置或状态文件。官方 JSON/分页/中文编码已由工具处理，失败不换命令绕过。

工具自己核验 Run 的实际发起人、群、角色和固定 Base。请求中禁止指定身份、应用、资源、命令、单价或总价。不要解析聊天用户自报的身份作权限依据。

## 选择动作

- 问安排：`query`。未给历史编号则查明确保存的当前轮次；新会话“刚才那单”先澄清。不要根据工作目录恢复旧指代。
- 询价、可能加桌：`query/estimate`，明确总桌数。用户说“加三桌”，先查当前真实桌数再换成总桌数；工具负责金额。询价不转成 `preview`。
- 明确修改：`preview/order.change`。限定总桌数、特殊菜单桌数及无海鲜套餐。补充纠正只提交明确改动项，工具合并本人同类待确认预览并替换短码；不要丢弃用户已说明的菜单范围。
- 宴会接收或反馈：先查询当前版，再 `preview/handoff.update` 带明确业务版本。用户指定的旧版本不能改写成当前版。单说收到只接收；“布桌没核对”是待落实；“有问题”必须有原因。没有接收的情况下，先问是否接收，也可将用户明确要求的接收与反馈合在一份预览。
- 开始新轮：`preview/demo.new_round`，再由 Owner 确认。保留旧轮记录；旧轮未办完的提示不能省略。
- 取消：`cancel`；查预览或不明结果：`status`。

## 确认与异常

仅明确 @本 Bot 的原发起人可以确认。真实当前消息仅包含“确认 六位码”时传给 `confirm`；支持大小写、全角和有无空格。引号、转述、否定、多个码或“确认但改成……”不能当作批准。夹带修改先修改预览，新码由工具生成。

预览不是保存成功。成功只认工具 `completed` 回读。`unchanged` 表示零写入；`busy` 表示群内已有操作或正在执行，可继续查询；`unknown` 先查证，不能取消后重建或反复写入；`conflict`、`invalidated` 按最新事实重新预览，不能沿用旧码。错误应说明尚未保存或结果待查证，不擅自宣称没有副作用。

## 回复

查询、预览、确认、取消和状态结果使用工具的 `reply_text`。不要展示内部 evidence、成员键、Run 标识和调试参数，不添加英文执行过程。必要追问用自然中文一次问清。

销售表达“客户已确定”只代表销售陈述；套餐不用于过敏风险判断；交接完成不表示现场已经交付。婚期、容量、单价、规则和客户均为固定虚构样例，不扩展为真实财务或合同承诺。
